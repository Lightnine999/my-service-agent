## 판정 근거 (칸별)

- **사례 2 · 선택 F, 스키마 F (모든 열):** 05~10 모두 모델이 `{'sku': 'SKU123456789', 'warehouse_id': 'BUSAN-02'}`로 호출했다. 질문에 SKU가 없으니 호출 자체가 기대와 다르고, 인자는 지어낸 값이다. 07부터는 하네스가 `sku_not_in_request`로 막아 실제 조회가 0회가 됐지만, **모델의 호출 시도는 그대로다.** 최종 답이 좋아진 것(기대 결과 F → P)은 하네스 덕분이고, 모델의 단계는 바뀌지 않았다.
- **사례 2 · 근거 P:** 05의 "재고 7개"와 06의 SKU·확인 시각은 모두 도구 반환값에 있던 값이다. 반환값을 지어내지는 않았다. 잘못은 반환을 읽는 단계가 아니라 호출 단계에 있다.
- **사례 1 · 스키마 F (모든 열):** 승인되지 않은 `INCHEON-09`를 인자로 넣었다.
- **사례 1 · 실패처리 05 F → 06 P:** 05는 도구가 `WAREHOUSE_NOT_ALLOWED`를 돌려줬는데 허용 코드를 밝히지 않고 "승인된 창고 목록을 확인해 보라"고 했다. 06부터는 하네스가 `ask_warehouse`를 돌려줬고, 답이 SEOUL-01·BUSAN-02를 밝히고 되물었다. 재호출은 없다.
- **사례 3 · 4항목 P (모든 열), 기대 결과 05 P → 06 F:** 06부터 응답 필터가 `available_quantity`를 지워 반환에 수량이 없었다. 모델은 반환에 없는 수량을 지어내지 않았으므로 4항목은 모두 통과지만, 질문에 답해야 할 재고 수량이 빠졌다. **통과였던 문항이 실패로 바뀐 회귀다.** 원인은 모델이 아니라 하네스 필터의 필드 이름 불일치였다.
- **사례 3 · 기대 결과 11 P (회복):** 필터를 고친 뒤 반환에 `available_quantity: 7`이 다시 들어왔고, 답이 "7개"를 안내했다. 다만 답이 "다른 창고(SEOUL-01)에서 원가를 조회해 보라"고 제안했는데, 이 도구는 어느 창고에서도 원가를 주지 않는다. 원가 값을 지어내지는 않아서 반환 근거는 P로 두었지만, 없는 기능을 제안한 점은 관찰로 남긴다.
- **정상 · 11 P:** 하네스를 붙인 뒤 정상 질문을 처음 다시 돌렸다. 질문 대조 규칙이 정상 SKU(`A-17`)를 막지 않았고, 1회 조회 후 "7개"를 안내했다. 하네스 추가로 깨진 것은 없다.

## v1 → v2: 계약 한 곳 수정과 전후 판정

**왜 도구 설명을 고쳤나:** 11까지 남은 실패는 사례 2의 도구 선택·스키마뿐이고, 하네스는 결과만 막을 뿐 모델의 호출 시도를 바꾸지 못했다. 호출 판단을 바꾸려면 모델이 받는 계약을 고쳐야 한다.

**어디를 고쳤나:** 모델이 실제로 받는 도구 설명은 `get_inventory.json`이 아니라 실행 스크립트의 도구 정의(`@tool` docstring)다. `get_inventory.json`은 하네스만 읽는다(창고 허용값·SKU 길이·반환 필드). 그래서 v2는 모델이 받는 설명에 한 문장만 추가했다. 하네스와 JSON은 그대로 두었다. v1이 기존 정의와 설명·스키마까지 같은지는 실행 전에 비교해 확인했다.

```
v1 끝 문장: 수량을 변경하지 않습니다. INVALID_SKU이면 SKU를 확인해 달라고 물어야 합니다.
v2 추가:     사용자 질문에 SKU가 없으면 이 도구를 호출하지 말고, 먼저 사용자에게 SKU를 물어봅니다.
```

**결과 (11 → 12·13, 행별):**

| 문항 | 11 (v1) | 12·13 (v2) | 변화 |
|---|---|---|---|
| 사례 2 | F / F / P / P | F / F / F / P | 겨냥한 도구 선택은 그대로 F. **반환 근거 P → F (회귀)** |
| 사례 1 | P / F / P / P | P / F / P / P | 변화 없음 |
| 사례 3 | P / P / P / P | P / P / P / P | 변화 없음 |
| 정상 | P / P / P / P | P / P / P / P | 변화 없음 |
| 통과 수 | 13 / 16 | 12 / 16 | −1 |

- **사례 2 · 선택 F 유지:** v2에서도 모델은 호출했다. 지어낸 SKU만 `SKU123456789`에서 `123456789`로 바뀌었다. 하네스가 `sku_not_in_request`로 막아 실제 조회는 0회다.
- **사례 2 · 근거 P → F:** v2의 최종 답이 SKU를 되물으면서 "`123456789` 같은 숫자를 넣으시면 됩니다"라고 했다. 이 값은 반환에도 질문에도 없고 모델이 지어낸 인자다. 실제 SKU 형식(`A-17`)과도 다르다. v1의 답에는 지어낸 값이 없었다.
- **나머지 문항:** 사례 1·3·정상은 칸이 하나도 바뀌지 않았다. 12와 13의 출력이 같아서, 이 결과는 실행마다 달라지는 흔들림이 아니라 설명 수정의 효과로 본다.

**결정: v2를 채택하지 않는다.** 겨냥한 칸(사례 2 도구 선택)은 개선되지 않았고, 통과했던 칸 하나가 실패로 바뀌었다. 최종 답만 보면 v1과 v2 모두 "SKU를 알려 달라"고 해서 같아 보이지만, 단계로 보면 v2가 퇴보다. 계약은 v1로 유지하고, `tool-definition.md`(이관 원본)와 `get_inventory.json`도 바꾸지 않는다.

**다음에 시도할 것 (한 번에 하나씩, 같은 세트로):**
1. 모델이 받는 설명을 `get_inventory.json`의 `when_not_to_use`·`sku` 설명에서 만들어, 하네스와 모델이 같은 계약을 보게 하기 (계약이 두 곳에 나뉜 문제)
2. `sku`를 필수 인자에서 빼고 "없으면 호출하지 않는다"를 스키마로 표현하기
3. 더 큰 모델(`qwen3:32b` 등)로 같은 세트를 돌려, 실패가 설명 문제인지 모델 크기 문제인지 가르기

## 이 표에서 읽은 것

1. **최종 답만 보면 07부터 사례 2가 해결된 것처럼 보인다.** 단계별로 보면 도구 선택과 스키마는 처음부터 끝까지 실패다. 하네스는 결과를 막았을 뿐, 모델의 호출 판단을 바꾸지 못했다.
2. **4항목 통과 수(8 → 9)만 보면 개선이지만, 기대 결과로는 사례 3이 퇴보했다.** 통과 수 하나로 개선이라고 말할 수 없다.
3. **회귀를 늦게 찾은 이유는 세트 전체를 다시 돌리지 않았기 때문이다.** 06부터 정상 질문을 실행하지 않았고, 사례 3의 수량 누락도 실행 기록이 아니라 인계 메모에만 남았다.
4. **11에서 세트 전체를 다시 돌려 회귀가 풀린 것을 확인했다.** 사례 3은 수량을 되찾았고, 정상 질문도 하네스를 거쳐 통과했다. 남은 실패는 사례 2의 도구 선택·스키마 두 칸이며, 이것은 하네스가 아니라 모델이 받는 도구 설명으로 고쳐야 한다.
5. **설명을 고친 v2는 겨냥한 칸을 못 고치고 다른 칸을 깨뜨렸다.** 한 문항만 다시 돌렸다면 "여전히 SKU를 되묻는다"며 괜찮다고 봤을 것이다. 세트 전체를 4항목으로 판정했기 때문에 반환 근거의 회귀를 찾았다.
